# HIGGS in the shared VR interaction services

An empty hand beside a pouch and a loose object offers two possible actions for the same grip. HIGGS owns that choice, the resulting hand use and its physical execution. A consumer supplies its eligibility and gameplay rule through the shared service. HIGGS can report the selected action and its observed outcome so another mod can cooperate with it.

The maintained [English concept](https://github.com/Vhodnoylogin/body-pouches/blob/main/docs/trinity-synergy/concept-en.md) and [Russian concept](https://github.com/Vhodnoylogin/body-pouches/blob/main/docs/trinity-synergy/concept-ru.md) live in Body Pouches. HIGGS owns hand state, input, action selection, possession, physical hand operations and haptics. PLANCK owns its NPC bodies and hit path, VRIK supplies the player pose, PPB supplies anatomy, and Body Slots manages logical interaction regions. Consumers retain inventory selection, crime, harvesting and other domain rules.

The proposed interfaces cover input and release correlation, scoped hand-use sessions, inventory/equipment execution routes, physical support and constraints, copied motion/contact observations and coordinated haptics. Clients negotiate each table and capability independently. Released interface 001 has its original declarations. New observer identifiers and mutation permissions have separate meanings, with explicit version negotiation for the experimental tables.

Every change to the author's gameplay path must enable one of those contracts. Input admission, physical request execution, actual result publication and lifecycle invalidation need calls from the existing runtime. Build declarations and exports connect the new implementation. Internal optimization and unrelated behavior repairs are outside this proposal.

Capability results describe supported operations precisely. A policy for trigger-originated weapon drawing requires a qualified semantic command provider. Exact equipment layouts require an executor that can observe and confirm all affected places and instances. Unsupported operations are rejected before mutation. The [implementation ledger](https://github.com/Vhodnoylogin/body-pouches/blob/main/docs/trinity-synergy/implementation-status.md) records source, build, consumer and game verification separately.

The experimental C SDK groups its existing exports into [hand ownership](../include/higgshandapi.h), [input](../include/higgsinput.h), [observations](../include/higgsobservations.h), [items](../include/higgstransactions.h) and [physical operations](../include/higgsphysics.h). Native physics providers can include [borrowed-body interop](../include/higgsnativeinterop.h) with its [common types](../include/higgsabitypes.h). Previously built clients keep the same exported symbols, table versions and layouts. Consumers rebuilding from earlier experimental headers can switch their include paths to these groups.

HandUseProposals version 2 adds an explicit shared decision window. A client enables it before gameplay with controls released. New eligible button, native grab, native mouth/shoulder release actions and nonbutton proposals collect until the next main maintenance, where persistent provider/action/target keys and effective action priority select a disjoint set before any executor starts. A pending button release cancels its offers; a selected native grab reaches the next held controller sample and retains its matching release. Native grip/trigger aliases for the same target share that native choice. Controls without an eligible candidate keep their default path. Reentrant proposals wait for the next window. Legacy immediate hand/domain/physical admission cannot bypass an enabled shared window; consumers first obtain a selected grant. Version 1 remains independently available with its original admission and ordering behavior when shared windows are absent.

Existing possession and authorized continuation are preserved. Pending native acquisition reserves its hand until delivery/acquisition or release; publishing the held item permits consumption and transfer while grip remains down. Revision-checked session expansion can enter the same window through ProposeResize: only newly requested hands compete, and rejection retains the original session. Renewal and reduction remain immediate. The production regression in [shared_rounds_tests.cpp](../test/shared_rounds_tests.cpp) covers mixed arrival orders, native release ownership, invalidation, reentrancy and handoff. The [self-contained contract test package](../test/README.md) compiles the current production service sources directly. These are offline source checks; game behavior remains unqualified.

The separate hand-surface interface performs a passive ray query from the current resolved palm in the current native world. It reports the nearest supported static or moving physics surface, including terrain, with a body UID and leaf shape key. Those identifiers provide copied query evidence and do not pin external body lifetime, identify anatomy, issue a grant or change physics. Support acquisition separately revalidates its target. The header declares the exact observation scope and lifecycle checks.

The optional `HeldReleaseInterface` closes the pouch release path. A registered recognizer receives one semantic pre-drop intent for the actual held item, after one factual post-update hand publication (bounded to100ms), and submits through the existing ordered candidate/routing service. Native mouth/stash actions compete in the same maintenance window. A semantic intent has its own ID and edge; it neither reuses a consumed hardware Up nor overwrites the original press sequence. No suitable offer resumes the original native release. Pending or committed/uncertain transfers cannot fall through into a duplicate drop. Transaction-driven physical releases bypass offering to prevent recursion.

For inventory withdrawals, the executor explicitly calls `FollowInventoryGrip(client, transferId)` after a completed, physically confirmed native grip and before releasing its original grant. HIGGS validates the owned receipt and original press; its matching release can then use the same native pre-drop path, including a release received during grip delivery. This opt-in is idempotent per transfer and does not change existing inventory consumers. Spatial pull-out recognition, slot policy, potion assignment and content persistence stay in Framework/consumer code. These18November additions were developed without running tests or the game; compilation does not establish gameplay parity.

`HIGGS_HAND_CAP_ACCEPTED_RECEIPTS` (Hand capability64) lets a dispatched generic executor opt into result retention before it admits any child. Once it accepts responsibility for queued work while the selected grant remains active and recognition is not waiting, it echoes the exact copied current `ACCEPTED` result through `ReportResult`. This records only the obligation to retain that result until `ReleaseGrant`; it creates no inventory receipt, stage transition or renewed authority. An exact repeat while still active is idempotent. Unstarted generic actions without this opt-in keep the existing finite-lease history behavior; admitted transaction children retain their separate automatic pin. Native and hand-use session actions do not opt in through this path.

Natural grant expiry ends hand and mutation authority even when a consumer has not yet observed its admitted inventory transaction. Tracking loss and routed-source invalidation also revoke hand/mutation authority, while preserving only the factual receipt channel when an admitted child exists. This applies to recognizer cancellation, revocation in its existing uncommitted scope, and recognizer-only client or routed registration removal, including already matched/dispatched actions; owning-consumer teardown remains distinct. Legacy generic recognizer submissions retain only client identity, so removing that whole recognizer client revokes them; registration-level revocation requires the routed submission identity. The parent and its exact correlated child receipt remain available for factual reporting; a successful late report must match the child's attested stage, flags, item and quantity. Both broker history and the actual transfer record remain pinned through terminal parent reports until the owning consumer acknowledges consumption with `ReleaseGrant`, after mirroring the outcome. An identical repeated `COMPLETED` report is idempotent and does not release that retention or renew authority. Removing the owning consumer client or its action executor, or changing epoch, ends this retention. Removing only the spatial recognizer, or cancelling UI/input, does not acknowledge the consumer's receipt. This does not admit a new transfer or reopen a cancelled action: a child already cancelled before factual completion still follows its existing compensation/recovery path. Explicit inventory-grip continuation after expiry also requires the unchanged original input context and the same published possession episode captured at completed native grip. A missing completed episode or a release/regrab of an equal reference cannot inherit the previous press; unavailability of this optional continuation does not disprove the completed transfer. These source-level lifetime corrections remain untested. Compilation and linking, where separately recorded, do not qualify runtime behavior; no tests, probes, installation or gameplay qualification were performed for these acknowledgement/source-invalidation changes.


The optional `HIGGS_InventoryEffectsInterface1` supplies the missing negative evidence without changing old action-result flags or tables. `CopyForAction` is read-only for a selected generic action's executor owner or recorded recognizer. Its 32-byte record summarizes only HIGGS-recorded inventory work under that action: `CLOSED` with neither `COMMITTED` nor `UNCERTAIN` positively means no recorded inventory mutation. A cancelled action with no inventory flag alone never establishes that fact. Frame/consumer code must still own its logical content projection; this service grants no inventory or hand authority.

Closure requires terminal parent state and no same-owner/epoch/grant authority, including entered native/operation work. Complete history is retained until acknowledgement; a private sticky child-seen bit prevents an acknowledged/evicted child from looking like no child was ever admitted. A genuine no-child cancelled action can be observed without a retention opt-in. Borrowed session grants remain uncertain because their existing child-input attribution can differ. A sticky unattributed-child marker also protects the original parent when a continuation routes a same-grant child to another input or hand set; removing that continuation cannot manufacture an empty child history. Active/recovery children, missing transfer records, unsupported domain children, overflow and incomplete history never become positive nonmutation. Confirmed prior inventory commitment remains visible even when the parent action itself was cancelled. The query uses the existing native dispatch/transaction/broker locks and introduces no callbacks, stage reopening, inventory mutation or new implementation file. It is source-reviewed and compiled only where a matching receipt explicitly records that build; no runtime tests were run for it.

`RESTORED` is aggregate evidence: closure, complete known child history and confirmed compensation of every recorded inventory mutation are all required. `COMMITTED` remains sticky, and any missing/uncertain child dominates an individual compensation. A generic parent compensation flag alone cannot establish that aggregate result. This distinction is opt-in observation; existing result layouts, flags and stage semantics stay unchanged.

The evidence contract requires every relevant inventory mutation to use the HIGGS transaction executor. Generic parent flags summarize those correlated transactions; they cannot assert an additional untracked mutation under this contract. Direct game inventory writes remain outside this observation and cannot be independently proved or compensated by it.
